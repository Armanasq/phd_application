## 2. Objective and operating assumptions
The repository combines faculty discovery, identity/email verification, professor literature enrichment, LLM-generated application outreach, approval-oriented draft review, SMTP delivery and IMAP reply tracking. It assumes an applicant-controlled private deployment, stored personal research profile, configured SMTP/IMAP credentials and human review. A draft-composition score is not a supervised admissions probability or permission to contact faculty. The code is useful for process engineering but should not become an autonomous unsolicited-email campaign.

## 3. Implemented components and information lineage
- [Search agent](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/agents/search_agent.py) assembles candidates from CSRankings and web results, checks duplicates by email/name/institution and enriches contacts/papers before saving. Source freshness and professor active recruitment still require direct first-party verification.
- [Composer](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/agents/compose_agent.py) uses an applicant profile, representative work and professor-specific research results; validates Chinese and English draft structure and writes pending drafts. Prompt constraints explicitly reject unsupported publication claims, but LLM compliance is not guaranteed without independently grounded sources.
- [Data persistence](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/core/database.py) stores professors, recommended papers, drafts with `pending/sent`, and IMAP replies. Inspectably uses SQL rows and source annotations; no applicant-level evidence ledger or proof of professor funding/visa eligibility was found in inspected paths.
- [Send service](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/services/send_service.py) loads the draft, checks `status == "sent"`, attaches local CV/transcript/papers, constructs MIME with optional CC, sends via TLS-capable SMTP and then updates sent status. Refused primary recipients are handled. [Tests](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/tests/test_send_service.py) check recipient refusal and default-CC gating with fake SMTP.
- [Reply tracker](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/services/reply_tracker.py) uses IMAP with batching and a lock for its check routine, maps replies by sender/subject and archives matched conversations.
- [Draft ranker](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/services/draft_review.py) assigns heuristic relevance and reply-likelihood **scores** from exact paper-title mention, metadata, research terms, subject specificity, recruiting tags and length. The code labels it `heuristic-v2`, with deterministic tests; it is not a statistically calibrated probability.

## 4. Verified source-level safety and reliability findings
1. **Outbound authorization gap at API boundary:** [`POST /api/send/{draft_id}` and batch route](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/api/routes.py) invoke `send_email`/`send_batch` directly. The inspected route signatures contain no auth dependency or user-scoped approval gate; [main app](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/main.py) attaches router and configures CORS, which does **not** establish authorization. The README's optional Cloudflare Access controls are deployment-dependent. Unprotected deployments would risk unauthorized sends with configured credentials; no exploit execution was attempted.
2. **Non-atomic delivery:** [send service](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/services/send_service.py) checks `sent` status before SMTP and writes sent status after SMTP success. Parallel send requests or a crash after SMTP receipt can cause duplicates; there is no atomic `approved -> claimed -> delivered` state transition or transactional outbox in this path. Primary-recipient refusal handling is a useful safeguard but does not solve at-least-once delivery.
3. **Approval is not server-side enforced:** the service accepts any draft status other than `sent`, so UI review alone does not prove authorized final send. An explicit persisted approval identity, timestamp and attached evidence should be mandatory before outbound effects.
4. **Misleading response metrics:** `reply_likelihood_score` is an arbitrary bounded heuristic, influenced by citation and publication-title string matching; [tests](https://github.com/Joky02/AcademiaReach/blob/ac8765fb0e559b1a5245e7b262765bf8173492dc/backend/tests/test_draft_review.py) validate ranking behavior, not held-out reply outcomes or calibration. Present as sorting weight only; never as a response probability.
5. **Research provenance limits:** email prompts request exact titles, while discovery/enrichment may rely on LLM-reported webpages. No independent checks here prove professor identity, recruitment status, papers, funding or personal fit.
6. **Credential and privacy boundaries:** local profile, transcripts and secrets are intended to be Git-ignored; deployment needs private server-side storage, SMTP/IMAP isolation, request authorization, attachment audit and egress controls. Private deployment claims depend on operator configuration.

## 5. Transferable engineering decisions
Adopt the conceptual sequence **verified professor identity → source-pinned research match → claim-checked draft → persisted human approval → idempotent authorized send → receipt/reply lineage**. Preserve bilingual and template-specific validation, separation of agent harness and model provider, source dedup, SMTP primary-recipient refusal handling, IMAP batching and explicit private configuration. For production rewrite: authenticated user/principal middleware, per-draft ownership and approval, optimistic concurrency/DB claim, idempotency key and delivery ledger, outbox worker with failure reconciliation, verified first-party faculty recruitment and no automated sending without permission.
