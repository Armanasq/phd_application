## Critical correctness and security observations
1. **Plaintext authentication:** [`server.js`](https://github.com/DianaJoseph08/phd-admissions-srm/blob/9e8d31a1d212790b58571ea2f247653643400c42/server.js) compares supplied password directly against `users.password` in SQL and changes it via raw `UPDATE users SET password = ?`. It also provisions an account with a hard-coded password literal in source. Password values are **intentionally not copied or repeated**. Require salted adaptive password hashing, per-user credential resets, removal of seeded credentials and mandatory secret rotation.
2. **Predictable bearer sessions:** the server constructs tokens from user ID and wall-clock timestamp, then stores them in an in-memory `Map`. That design is guessable in principle and loses sessions on restart. Require cryptographically random session tokens, expiration, revocation and secure cookie handling. Role-based `requireAuth` guards exist but are not sufficient if authentication primitives are weak.
3. **Response leaks credential column:** the admin user-list SQL selects `u.password` and returns all selected user records to clients. This exposes sensitive authentication fields even to legitimately authorized administrators and broadens compromise impact; strip password columns from all API responses and logs.
4. **Uncontrolled applicant uploads:** multer builds filenames using a timestamp plus unsanitized `file.originalname`; [server](https://github.com/DianaJoseph08/phd-admissions-srm/blob/9e8d31a1d212790b58571ea2f247653643400c42/server.js) mounts multiple upload directories through public static paths. Depending on path normalization, deployment and filesystem permissions, this can permit access to confidential uploaded documents. Do not expose file objects through unauthenticated static directories; use private storage and authorization checks.
5. **Tracked binary DB:** the public tree includes a nontrivial SQLite `phd_admissions.db`; this is a privacy and data-governance red flag even if its contents are merely fixtures. No claim about specific people or records is made because the database was not inspected. Remove/replace only after a formal retention and exposure assessment, and ensure no genuine applicant files are committed.
6. **Persistence/migration:** initial setup issues many `ALTER TABLE` statements and ignores errors, while selection paths implement narrow transactional boundaries. No formal migration-version ledger or end-to-end compatibility tests were observed from inspected files.
7. **Operational boundaries:** the listener defaults to `0.0.0.0`, increasing exposure risk when deployed without perimeter access control. The installed `package.json` describes version 1.0, but release quality is not substantiated by tests.

## Transferability and country relevance
The useful abstraction is **institution-scoped state machine with explicit reviewer ownership, stage guards, rank-release evidence, quota constraints and transactionally updated supervisor allocations**. Do not copy personal data, password/session schemes, seeded accounts, upload routes or institution-specific policy as a universal admissions decision rule. This repository's Indian institutional processes cannot prove admissions/funding terms in Germany, Switzerland, the Netherlands or the other targeted jurisdictions.
